# kern — Research report (spec §14, PLAN.md 4.3)

**Date:** 2026-10-26. **Scope:** the feasibility result of Phase 0, the measured performance of Phases 2 and 3, the agent experiment of Phase 4, and the comparison with every reference direction of spec §14. Every claim about another language cites a primary specification or paper from `docs/references.md` by its bracketed key; `tests/citations_test.go` enforces it.

## 1. Question and thesis

Can a systems language whose *only* ownership mechanism is second-class access (`view`/`edit`/`own`/`out` parameter conventions, lexical `with`/`match`/`for` bindings, no first-class references) be safe, run within 10% of C and Rust [rust-reference], and be easier for AI agents to program against when its compiler explains ownership and cost structurally? The thesis has three measurable parts: feasibility (Phase 0), performance (Phases 2–3) and the agent metric (Phase 4).

## 2. Feasibility (Phase 0)

The Phase 0 gate was **GO** (`docs/reports/phase-0.md`): the checker prototype accepts the five required programs (vector, B-tree split/merge, arena AST, zero-copy parser, thread handoff) and every accepting twin, rejects each statically enforced rule's negative fixture with exactly one diagnostic naming one rule, and the thirteen §8 workload notes classify ten workloads as expressible in the core, three as requiring audited unsafe internals behind a safe API (buffer pool, intrusive run queue, lock-free queue), and **none** as requiring the reserved view-kinded-aggregate extension, so the extension was not scheduled. Phases 1–3 then implemented the full language with these results against the design:

- Every §5 rule is enforced by one of 60 registered diagnostics, each with a reject fixture and an accepting twin; the interpreter and the native backend agree on 120 executable fixtures (output, trap kind and span).
- The three workloads with unsafe internals needed, in total, two assertions and fifteen `unsafe` blocks, each under a contract block (`docs/unsafe-audit.md`); the other ten workloads are safe code.
- Two language additions were needed beyond the v0.2 spec to write the workloads idiomatically: array literals and the wrapping arithmetic intrinsics named by §4.1. Nothing required references.

## 3. Performance (Phases 2 and 3)

`bench/REPORT.md` (generated; 5 runs per row, 95% confidence intervals, Apple M4 Pro, clang 23.1.4, rustc 1.99.0, go 1.27.3; the run of 2026-10-30 at a one-minute load of 2.1 to 2.4, `docs/reports/thread-pool-job-path.md`) measures all thirteen §8 workloads in C, Rust [rust-reference] and kern with the same checksums. kern release against the better of C and Rust:

| Workload | throughput ratio | RSS ratio | 10% targets met |
|---|---|---|---|
| vector | 1.17 | 1.00 | both |
| hash_table | 0.91 | 1.06 | both |
| btree | 0.87 | 1.23 | neither |
| arena_ast | 0.91 | 0.99 | both |
| ring_buffer | 1.16 | 1.03 | both |
| wal | 0.99 | 1.00 | both |
| packet_parser | 0.92 | 1.06 | both |
| buffer_pool | 0.97 | 1.01 | both |
| page_frame_allocator | 0.97 | 1.03 | both |
| intrusive_run_queue | 0.96 | 1.04 | both |
| thread_pool | 0.94 | 1.02 | both |
| lock_protected_map | 1.25 | 1.06 | both |
| lock_free_queue | 0.85 | 1.03 | RSS |

Eleven workloads meet both targets, eleven meet the throughput target and twelve the memory target; the two throughput misses of this run, btree at 0.87 and lock_free_queue at 0.85, read 1.01 and 0.93 when C and kern are interleaved on the same host minutes later (`docs/reports/thread-pool-job-path.md`), so they are the harness's row ordering rather than the programs, and are counted as the run measured them. The first report of this phase (`docs/reports/phase-4.md`, 2026-10-26) had three workloads meeting both, with the container-heavy ones at 0.25 to 0.52 of C; the difference is the sequence of engineering reports under `docs/reports/`: the containers rewritten in kern over the raw-pointer core (`containers-in-kern.md`), `Pool` growth through `realloc` (`btree-rss.md`), internal linkage and a union layout without a padding slot (`gap-diagnosis.md`), kern-level inlining with callees judged as lowered and loops admitted (`inliner.md`, `inliner-sizing.md`, `inliner-loops.md`), bit-count and byte-order intrinsics (`throughput-gaps.md`, `byte-order-reads.md`, `byte-order-stores.md`), `Vec.extend` and zeroed `Vec.resize` (`vec-extend.md`, `hash-table-gap.md`), release handles without identity tags and `Pool` slot metadata beside the element (`release-handles.md`), an owner-checked default mutex and condition variables (`quiet-harness-2026-10-28.md`, `condvar.md`), and the runtime's own parking lock in place of the pthread mutex (`perf-gaps.md`). None of these changed the ownership model: the gap was the C runtime boundary, the shape of the generated code and the synchronisation primitives, as the §9 separations had attributed it. What remains is the memory of a checked handle (btree, ADR-014) and the harness's own between-run variance: lock_protected_map went from 0.57 to 0.76 with the cheaper mutex and to 1.25 with the runtime-owned lock, whose owner word shares the lock's line and is written only by the holder, while thread_pool went from 0.59 to 0.88 with condition variables and to 0.94 on a quiet host, its remaining checks attributed at one or two points each and the C pool's own speed found to vary by 15% with the host's state (`thread-pool-job-path.md`). The `[unproven]` aliasing experiment still measures no throughput change from the §5.4 `noalias`/`readonly` attributes.

## 4. The agent experiment (Phase 4)

`bench/agent/` holds the experiment: ten tasks drawn from the §8 workloads (implementation, debugging, refactoring, optimization, unsafe-contract review), each with hidden tests (expected output, a clean check, and for the optimization and refactoring tasks a bound on allocation sites or copies measured through the machine API), reference solutions validated by the harness, and a tool-driving harness that records every tool call. The two arms receive the same language reference, grammar, prelude and examples; the structured arm gets JSON diagnostics with rule numbers and the semantic queries (`explain_ownership`, `show_copies`, `show_allocations`), the plain arm gets text diagnostics only. The aggregation rule closes spec §13 accepted gap 7: a trial succeeds only if the hidden suite passes within 20 iterations and 30 minutes, a failure scores the budget maximum, and a task is a win only when, for every model, the structured arm is strictly better than the plain arm in the first of these that differs: successful trials, then median iterations; a tie in both is a loss, and wall-clock time is reported but not compared. That is the rule as revised on 2026-10-28 (`docs/reports/agent-metric-revision.md`); as first written it required strictly lower medians of both iterations and wall-clock time, with successes only as a floor, and both results below are given under both forms.

**Result** (`bench/agent/REPORT.md`, 2026-10-28; models claude-opus-5-5 and gpt-6.1-sol, 5 trials per task, model and arm, 200 trials): every trial succeeds in both arms, and the primary metric records **0 wins of 10**, below the threshold of 8. The medians tie on iterations in every task (3 for claude-opus-5-5, 5 for gpt-6.1-sol, in both arms) and the wall-clock medians differ by a few seconds in either direction; no regression and no unsafe code beyond the task that asks for it were recorded. Both forms of the rule count a tie as a loss, so the result is 0 of 10 under either, and the experiment does not show that structured diagnostics help, and it does not show that they do not: the ten tasks are solved on the first attempt by both models from the language reference alone, so they cannot separate the arms. A test of the hypothesis needs tasks that the plain arm fails or takes several corrections on, which these ten, written to validate the harness, are not.

A second suite (`bench/agent/tasks-v2/`, with the first kept as `bench/agent/tasks-v1/`; `docs/reports/agent-tasks-v2.md`) was written to that end: each task states a requirement in terms of what the compiler's analyses report (a bound on copies, allocation sites, runtime-checked bounds checks or a type's size, or an exact destruction order) in a program of 60 to 130 lines whose sites are not all visible at a glance, the prompt gives the requirement but neither the rule behind it nor the sites, and the hidden suite checks the requirement through the same analyses; the structured arm's query set grows to the §7 commands those requirements are stated in (`show_bounds_checks` and `show_layout` beside the three above). Every reference solution passes and every starting source fails its hidden suite.

**Result on the second suite** (`bench/agent/REPORT.md`, 2026-10-28, same models, trials and budgets, 200 trials): under the rule as first written the primary metric again records **0 wins of 10**, now for the opposite reason; under the revised rule it records **1 win of 10**. The structured arm succeeds in 100 of 100 trials and the plain arm in 90: it fails the two tasks whose requirement is a bound on runtime-checked bounds checks (t03 on 6 of 10 trials across the models, t10 on 4 of 5 claude-opus-5-5 trials), every time by declaring the task done with a program that prints the expected output but leaves more checks unproven than the budget allows, a count the text diagnostics do not carry and `show_bounds_checks` does. On the other eight tasks both arms meet the budget at or near the first attempt, and there the queries cost iterations: the models call them in three quarters of the structured trials whether or not the task needs them, so gpt-6.1-sol's structured medians run one to five iterations above its plain medians on seven tasks, and claude-opus-5-5's tie on seven. Under the original rule each model wins two tasks, no task in both, and a tie is a loss: 0 of 10. The second suite therefore separates the arms, and what it shows is a reliability gain (ten failures in a hundred become none) that a rule comparing medians of speed, with successes only as a floor, could not register. The rule was revised on that evidence to compare successes first and median iterations second, with wall-clock reported and not compared (the noisiest measure: on t06 the arms tie on every trial's iterations and the wall medians differ by under a second). Re-scored from the same records, the second suite gives 1 win of 10: t03, where the structured arm has more successes in both models. t10 is not a win because gpt-6.1-sol's plain arm succeeded in all five trials one iteration faster, and the other eight are ties or plain-arm wins on iterations. The metric does not pass under either rule, and no rule that puts successes first would pass it on this suite: eight of its ten tasks gave the structured arm nothing to be better at. A suite built from the pattern of t03 and t10, a requirement only the compiler measures in a program whose first running version does not meet it, is what the threshold of 8 of 10 presumes.

A third suite (`bench/agent/tasks/`; `docs/reports/agent-tasks-v3.md`) was written on the same day from that result: every one of its ten tasks bounds the number of runtime-checked bounds checks, the one requirement the plain arm cannot verify from the language reference, and each is built on index forms whose habitual guards the proof pass does not accept (a cached length, a recomputed or converted index, a two-cursor `&&` loop, a range loop, a second store under one guard), so that a program which is correct and guards every index in the usual way is still over budget. Every reference passes and every starting source fails its hidden suite; the suite has not been run, by the owner's decision on cost, so whether the structured arm finds the proven forms from the query's labels within the iteration budget is not known.

The secondary comparison with Go and Rust agents [go-spec] [rust-reference] is descriptive only and was not run: both languages dominate model training corpora while kern is absent from them, so a difference in either direction would measure familiarity rather than the effect of structured diagnostics.

## 5. Comparison with the reference directions

**Hylo and mutable value semantics.** kern's conventions are the Hylo parameter passing conventions `let`/`inout`/`sink`/`set` under the names `view`/`edit`/`own`/`out`, and its projections are Hylo's subscripts restricted to lexical scopes [hylo-mvs] [hylo-tour]. The difference is that kern has no first-class references at all and no inferred lifetimes: a projection lives for a `with`/`match`/`for` block or a statement, and functions that return projections obey the elision rule (one access parameter), where Hylo's projections are tracked by the compiler across arbitrary expressions. The Phase 0 result shows the restricted form suffices for the thirteen workloads; the cost is the cursor rewrites noted in `docs/reports/phase-0-workload-summary.md` (an index cursor instead of a stored view).

**Second-class values.** The design is a direct application of Osvald et al.'s second-class values: accesses may be passed down the stack and never stored or returned beyond their source, which is exactly the escape rule kern enforces (`ACC_ESCAPE_STORE`, `ACC_ESCAPE_RETURN`) [osvald-2016]. Their later work shows that borrowing can be recovered on top of second-class values with a small set of rules [osvald-2017]; kern's elision rule and multi-access returns are that recovery, kept deliberately smaller.

**Swift nonescapable types and lifetime dependence.** Swift's `~Escapable` types and lifetime dependencies attach the dependence to the type and infer it at function boundaries [swift-se-0446] [swift-lifetime-pitch]. kern makes the same guarantee without the type-level marker by forbidding escape altogether; Swift's experience that annotation-free lifetime inference needed an explicit extension is evidence for keeping escapes out of the core rather than inferring them.

**Mojo origins.** Mojo moved from annotation-free references to explicit origins and then interior origins across its releases [mojo-origins] [mojo-24-6] [mojo-1.0]; the sequence shows a reference-based design growing annotations as it meets real programs. kern avoids the growth by not having references; its `Interior` marker (for `Mutex`, `Atomic`, user types under `unsafe assert Interior`) is the only analogue and is a property of a type, not of a reference.

**Rust.** Rust remains the expressiveness baseline: ownership, borrowing with inferred lifetimes, `Send`/`Sync`, and `unsafe` with the obligations the Rustonomicon spells out [rust-reference] [rustonomicon]. kern reproduces the ownership and `Send`/`Share` markers (derived, with `unsafe assert` as the escape), replaces borrowing by second-class access, and replaces drop flags and unwinding by static moves and traps (ADR-003, ADR-006): a moved variable is a compile-time fact, so no drop flag exists, and a trap runs no destructors, so no landing pads exist. The price is that conditional moves are errors rather than runtime-tracked, which the fixtures show to be a small restriction in practice.

**Zig, Hare and Go.** Zig's explicit allocators and absence of hidden control flow are shared by kern's allocator interface and trap model [zig-ref]; Hare's minimal runtime and replaceable startup match the freestanding mode of Phase 3 [hare-spec]; Go contributes the single-tool workflow and the convention that the compiler, not an external tool, answers the questions a developer or agent asks [go-spec].

**Austral.** Austral's linear types with borrow regions give the same no-aliasing guarantee with explicit region annotations [austral-spec]; kern's lexical binding scopes are the regions, written by the block structure rather than by name.

**Vale.** The `Pool` handle design (index, generation, identity tag, with generation retirement at wrap) is Vale's generational reference adopted as a library type rather than a language feature [vale-genrefs]; `tests/trap/generation*.kern` and `identity*.kern` are its checks.

**Cyclone and Tofte–Talpin regions.** Region type systems were rejected as a type-system feature (ADR-002): Cyclone's region annotations and Tofte–Talpin inference both put regions in types [cyclone-2002] [cyclone-regions-2002] [tofte-talpin-1997], where kern's arenas and pools are library types with Copy handles and no region in any type.

**Pony.** Pony's reference capabilities inform kern's `Send`/`Share` derivation, which keeps only the two capabilities needed for the scoped-spawn rule (the one cross-thread borrow) rather than Pony's six [pony-caps-2015].

**Ada and SPARK.** Contract blocks on every safe wrapper over unsafe internals follow Ada's pre- and postconditions and SPARK's proof obligations as documentation rather than as proved properties [ada-rm] [spark-rm]; kern enforces their presence (`UNSAFE_MISSING_CONTRACT`), not their truth.

**C++20 memory model.** kern's atomics are the C++20 orderings with the same happens-before and release-sequence rules [iso-cpp20]; the litmus fixtures under `tests/concurrency/litmus/` and the ThreadSanitizer runs are the evidence that the native lowering preserves them.

## 6. Conclusions

1. Second-class access as the sole ownership mechanism is **feasible** for the thirteen workloads: no workload needed references, three needed audited unsafe internals, and the checker's rules each have a fixture.
2. The performance target holds for eleven of the thirteen workloads in throughput and twelve in memory, container-heavy ones included, once the containers were written in kern and the generated code, the handles and the synchronisation primitives were brought level with the C versions; the two remaining throughput gaps are mutex-bound workloads at 0.88 and 0.76, and the one memory gap is the generation a checked handle carries. The ownership model cost none of the throughput.
3. The agent metric does not pass on either task suite, for opposite reasons. On the first, all 200 trials succeed in both arms and the tasks do not separate them. On the second, whose requirements only the semantic queries measure, the structured arm succeeds in 100 of 100 trials and the plain arm in 90, failing exactly where a requirement needs a count the text diagnostics do not carry; but the queries cost iterations on the tasks that do not need them. The aggregation rule was revised on that evidence to weigh successes before median iterations, and under it the second suite scores 1 win of 10 (0 under the original rule). The harness, both suites and both forms of the rule are in place and auditable; the reliability gain is real and measured, and the threshold of 8 wins presumes a suite on which most tasks stretch the plain arm, which two of these ten did.
