# AI-Native Systems Programming Language
## Research and Implementation Specification — v0.2
**Status:** Proposal, revised after architecture evaluation (see `ARCHITECTURE_EVALUATION.md`). Items marked *[ADR-n]* are architecture decision records (ADRs) with recorded alternatives; items marked *[unproven]* (none remain after Phase 5; each resolution names its experiment) require a Phase 0 experiment. **Date:** 2026-10-26. **Working name:** kern. Acronyms are defined in §15.

## 1. Vision
Create an AI-first, human-readable, native ahead-of-time systems language capable eventually of building operating systems, databases, compilers, embedded software, and performance-critical applications. Seek C/Rust-class runtime performance, no mandatory garbage collector, explicit resource costs, strong memory and concurrency safety for safe code, and minimal freestanding runtime dependencies.

The hypothesis is that AI agents benefit from predictable semantics, structured compiler feedback, and verifiable invariants more than from syntactic shortcuts. Do not remove useful features simply because they are advanced: retain features when their semantics are small and their costs predictable.

**Central design decision:** Safe code has no first-class references. Temporary access to a value is *second-class*: it exists only as a parameter convention or a lexically scoped binding, and it must never be stored, captured, or returned except by the single elision rule in §5.3. This is the discipline formalized by Osvald et al. (OOPSLA 2016) and used by Hylo's mutable value semantics. It removes lifetime annotations by removing the values that would need them. The known expressiveness cost (reference-holding aggregates such as borrowing iterators) is accepted for the core and addressed by one reserved extension (§5.6).

## 2. Goals, non-goals, and acceptance criteria
### 2.1 Goals (required eventually)
x86-64 and AArch64 native code; Linux/macOS development; freestanding targets; deterministic destruction; configurable allocators; C ABI; structs and layout control; atomics, SIMD, volatile MMIO, raw pointers and inline assembly in unsafe code; predictable allocation and dispatch; structured agent-facing tooling.

### 2.2 Non-goals (out of scope for this specification)
Full operating system, production database, self-hosting, package registry, async runtime, class inheritance, reflection, elaborate macros, general theorem proving, a feature-complete IDE, escaping closures, first-class references in safe code, regions in the type system, recoverable panics, and the concrete grammar, module system, and generic-constraint syntax (those are the language-reference deliverable of Phase 0, §11, and are gated separately).

### 2.3 Acceptance criteria (targets, not promises)
- Throughput within 10% of optimized equivalent C/Rust on the §8 suite, reported separately for (a) user-level code written with safe handles and conventions and (b) standard-library containers that use audited unsafe internals.
- Peak resident set size within 10% of the equivalent C/Rust implementation for equivalent representations.
- Negative safety tests: every statically enforced rule in §5 (those naming a diagnostic code) has at least one fixture that `check` rejects with exactly one diagnostic code citing exactly one rule number, and one accepting twin. Every runtime-enforced rule in §4.1, §5.3, §5.6, and §6 (those that trap) has at least one executable fixture whose expected output is a trap of the specified `TrapInfo` kind, and one twin that completes normally.
- **Primary agent metric:** within this language, agents given structured diagnostics and semantic queries (§7) reach a passing hidden test suite in fewer iterations and less wall-clock time than agents given plain text diagnostics for the same tasks, on at least 8 of 10 tasks. Cross-language comparisons against Go and Rust are reported but are descriptive only, because training-data volume confounds them.
- Every benchmark report records, per workload and per build configuration, over at least 5 repeated runs with 95% confidence intervals: binary text-section bytes, heap allocation count, compile time in milliseconds, and the number of source lines inside `unsafe` blocks.

## 3. Governing principles
1. Minimize *semantic* complexity, not keyword count.
2. Make heap allocation, deep copies, dynamic dispatch, synchronization, and bounds checks explicit or compiler-inspectable.
3. Never confuse AI-produced claims with compiler-established proofs.
4. Canonical formatting, unambiguous resolution, stable error codes.
5. Safe subset has precise guarantees; unsafe boundaries have documented obligations.
6. Design around realistic workloads before fixing syntax.
7. Keep the required runtime small enough for freestanding environments.
8. Allow machine-readable semantic edits without abandoning readable source.
9. One ownership mechanism. Arenas, pools, handles, and synchronization are library types built on it, not additional type-system features.

## 4. Candidate surface language
Go-inspired grammar: functions, nominal structs, tagged unions, exhaustive matching, arrays, slices, loops, modules, local type inference, explicit errors, and monomorphized generics. No inheritance, implicit coercions, function/operator overloading, or unrestricted macros initially.

**Function values.** Plain function pointers (for example `func(view[]u8) -> u64`) are first-class `Copy` values. They must not capture. Callback and thread-pool patterns use a pair of a function pointer and an owned context value (§5.5). **Closures are deferred.** When added, non-escaping closures are second-class values under the rules of §5.3 and introduce no new ownership machinery. Escaping closures are a non-goal (§2.2).

**Evaluation order.** Within an expression, operands are evaluated left to right. In a call, the callee expression is evaluated first, then arguments left to right; each argument's access or move takes effect when that argument is evaluated. In an assignment `place = expr`, `expr` is evaluated first, then the previous value of `place` is destroyed, then the new value is stored.

Illustrative pseudocode only:

```text
module storage
struct Page { id: u64; data: [4096]u8 }
union Result[T,E] { Ok(T); Err(E) }
func checksum(data: view[]u8) -> u64 {
    total := 0u64
    for b in data { total = total + u64(b) }   // b is a copy: u8 is Copy
    return total
}
```

`for x in p` over a place or view yields a copy of each element when the element type is `Copy`, and a per-iteration `view` (or `edit`, when iterating an `edit`) otherwise.

### 4.1 Execution semantics (normative for the Phase 1 subset)
These rules are the behavioral oracle shared by the interpreter and every native backend. Undefined behavior must not be reachable through safe language constructs.
- **Integer types:** `i8 i16 i32 i64 u8 u16 u32 u64 isize usize`; `isize`/`usize` have the target pointer width. Two's complement representation.
- **Arithmetic** (trap kinds per §6 in parentheses): `+ - *` and unary negation on integers trap on overflow in every build configuration (`overflow`). The explicit alternative forms are exactly: `wrapping_add`, `wrapping_sub`, `wrapping_mul`, `wrapping_neg`, `wrapping_shl`, `wrapping_shr` (the wrapping shifts mask the count to `width - 1` and never trap); `saturating_add`, `saturating_sub`, `saturating_mul`; and `checked_add`, `checked_sub`, `checked_mul`, `checked_div`, `checked_rem`, `checked_shl`, `checked_shr`, which return `Option[T]` (`union Option[T] { Some(T); None }`) with `None` where the trapping form would trap. Signed division truncates toward zero and the remainder takes the sign of the dividend, so `a == (a / b) * b + a % b` always holds. Division and remainder by zero trap (`div_zero`); dividing the minimum value of a signed type by `-1` traps (`overflow`). Shift counts are of type `u32` (so a negative count is not expressible); a count greater than or equal to the operand width traps (`shift`). Right shift of a signed value is arithmetic (sign-extending); right shift of an unsigned value is logical; left shift on either traps when a set bit is shifted out (`overflow`). Conversions between integer types are explicit. For every source and destination type, `T(x)` yields the mathematical value of `x` when it lies within the range of `T`, for any combination of widths and signedness (so `u16(i8(-1))` and `i8(u8(200))` both trap), and otherwise traps (`conversion`). `truncate[T](x)` never traps: it yields the low `width(T)` bits of the two's complement representation of `x` (sign- or zero-extended first when `T` is wider), interpreted in `T`'s signedness. The bit-count operations `count_trailing_zeros`, `count_leading_zeros` and `count_ones` are library intrinsics on any integer type returning `u32`; they never trap, and the trailing- or leading-zero count of a zero operand is the operand width.
- **Prelude sequence operations:** `Vec[T].extend(src: view[]T)` appends the elements of `src` to a vector whose element type is `Copy` (`CONSTRAINT_UNSATISFIED` otherwise) by one reservation for `len + len(src)` (checked arithmetic; a failed allocation traps `oom`) and one block copy of the elements, so a loop of `push` calls over a byte sequence is written as one `extend`. Beneath it, `ptr_store_seq(p, src)` writes the elements of a sequence view into raw memory at `p`; it is an unsafe operation with the §6 obligations (the destination is writable for `len(src)` elements and does not overlap the source).
- **Floats:** `f32`, `f64` are IEEE 754 binary32/binary64 with round-to-nearest-even; the compiler must not reassociate or otherwise perform value-changing float optimizations; not-a-number values propagate per IEEE 754; float-to-integer conversion truncates toward zero and traps (`conversion`) when the value is not-a-number or, after truncation, outside the destination range; the `saturate` form instead yields the destination's minimum or maximum for out-of-range values and 0 for not-a-number.
- **Bounds:** every index and slice operation on arrays, slices, and views is checked and traps on failure, unless the compiler records a proof fact (§7) that eliminates the check or the operation is the unsafe unchecked form.
- **Layout:** struct fields are laid out in declaration order with the target C ABI alignment and padding; a union's discriminant is at offset 0, is `u8` when the union has at most 256 variants and `u16` otherwise, and numbers variants from 0 in declaration order (a union with more than 65,536 variants is `TYPE_TOO_MANY_VARIANTS`); the payload begins at the next offset aligned to the maximum alignment of all variant payloads, the union's size is that offset plus the largest payload size rounded up to the union's alignment, which is the maximum of the discriminant's and the payloads' alignments; `[N]T` is `N` contiguous elements; a sequence access (`view[]T`/`edit[]T`) is a (pointer, length) pair of two `usize`; a scalar access is one pointer. `show-layout` reports the exact result. Reordering is never performed implicitly; `packed` layout is an unsafe attribute. A `packed` struct whose fields hold an `Atomic` inline (directly, or through arrays, tuples, structs or unions) is `TYPE_PACKED_ATOMIC`: an atomic cell keeps its natural alignment.
- **Endianness:** the target's native byte order; byte-order conversions are explicit library operations.
- **Error propagation:** `expr?` on a `Result[T, E]` returns `Err(e)` from the enclosing function, destroying owned locals of exited scopes in reverse declaration order (§5.1), and yields `T` otherwise.
- **Traps:** per §6. A trap is observable only as termination (plus optional hosted cleanup); no safe construct observes a trap and continues.

The concrete grammar, module resolution rules, and generic-constraint syntax of the Phase 1 subset are not defined by this document (§2.2). They are Phase 0 deliverable (1), delivered as `spec/grammar.ebnf` and `spec/types.md`, and Phase 1 must not start until that deliverable is accepted.

## 5. Ownership model — behavioral requirements
**Safety contract:** Safe code must prevent use-after-free, double-free, dangling references, uninitialized reads, unsynchronized mutable aliasing, and data races. This does *not* imply all array bounds or overflow conditions are proved statically; runtime checks are permitted where stated. Unsafe code and FFI are trusted boundaries.

### 5.1 Unique ownership and moves *[ADR-1, ADR-3]*
- Every value has exactly one owner: a variable, a field, an array element, or a slot in a library container. Destruction occurs exactly once, at scope exit of the owner, unless ownership is transferred.
- **`Copy` derivation.** Integer, float, and `bool` types, raw pointers, function pointers, and container handles (§5.6) are `Copy`. A struct, union, or array type is `Copy` iff it declares no destructor (§5.7), does not opt out of `Copy`, and every field or element type is `Copy`. Every other type is **move-only**. A field is an **owning field** iff its type is move-only; thus an aggregate is move-only iff it has a destructor, opts out, or has an owning field. `Copy` values are duplicated bitwise on use.
- Deep copies are explicit (`copy(x)` or a `clone` method). There is no implicit deep copy or hidden heap promotion.
- Moves are implicit at any by-value use of a move-only value: passing to an `own` parameter, assignment, return, or storing into a field or container. A move invalidates the source.
- **Moved-ness is static.** At every program point the checker knows whether each variable is owned or moved. A control-flow join where one predecessor moved a variable and another did not is an error (`OWN_CONDITIONAL_MOVE`) unless the variable is never used again on any path including scope exit; the machine-applicable fix inserts `drop(x)` on the non-moving path. Consequence: every destructor call site is static in the IR (implementation note, non-normative: no drop flags are needed).
- **No partial moves.** Moving out of a field or element is an error (`OWN_PARTIAL_MOVE`). Use `take(place)` (moves the value out, leaving the type's declared default, which the type must define) or `replace(place, v)`. Move tracking is therefore per variable.
- Definite initialization is flow-sensitive. Reading a variable or field before initialization on any path is `INIT_UNINITIALIZED_READ`.
- An ordinary local is initialized only as a whole: by a whole-value expression, or by being passed as an `out` argument (§5.2). Assigning a field of an uninitialized local is `INIT_FIELD_OF_UNINITIALIZED`. Per-field initialization exists only inside a callee for its `out` storage. Consequently a partially initialized ordinary local never exists, and an uninitialized local leaving scope is destroyed as a no-op.
- Reassignment of an owned variable destroys the previous value first (order per §4). Early return and error propagation destroy all owned locals of exited scopes in reverse declaration order. Recursion creates one owner per activation.

### 5.2 Parameter conventions *[ADR-1, ADR-5]*
Four conventions, written on the parameter and chosen by the callee:

| Convention | Meaning | Caller passes | Callee obligations |
|---|---|---|---|
| `view[T]` | read-only, non-escaping | any place of type `T`, or an existing view | must only read; is permitted to pass it down as `view` and to return a projection of it (§5.3) |
| `edit[T]` | exclusive mutable, non-escaping | a mutable owned place, or an existing edit | is permitted to read and write in place, to pass it down as `view` or `edit`, and to return a projection of it (§5.3) |
| `own T` | ownership transfer | an owned value (moved) or `copy(x)` | must destroy or move the value on every path |
| `out T` | initialize uninitialized storage in place | an uninitialized local, or a fresh slot provided by a container | must initialize the whole value on every normal-return path (`INIT_OUT_NOT_SET` otherwise); see failure rule below |

**Scalar and sequence access.** `view[T]` and `edit[T]` denote access to exactly one value of type `T`. `[]T` is the slice type: an unsized contiguous sequence of `T` with a length. `view[]T` and `edit[]T` are shorthand for `view[[]T]` and `edit[[]T]`: access to a sequence, with `len(v)` defined, element projection `v[i]`, and sub-slice projection `v[i:j]`. An array place `[N]T` coerces to a sequence access at a call site. A scalar access is represented as one pointer; a sequence access as a (pointer, length) pair.

`view` and `edit` are **second-class**. They must not be stored in a struct, union, array, or container (`ACC_ESCAPE_STORE`); must not be returned except under §5.3 (`ACC_ESCAPE_RETURN`); must not be captured; must not be live across a thread spawn except a scoped spawn (§5.5, `ACC_LIVE_ACROSS_SPAWN`); and must not be live across any future suspension point.

**`out` failure rule.** Within the callee, initialization of `out` storage is tracked per field, statically, like any other definite-initialization state. On an error-return path (any `return Err(...)` or `?` propagation), the compiler inserts destruction of every field of the `out` storage that is initialized at that point, in reverse initialization order; the caller then observes the storage as uninitialized. If the whole value is initialized and the callee then returns an error, the whole value is destroyed by the ordinary rule of §5.7 (type destructor first, then fields); the per-field rule applies only while the value is partial, and no type destructor runs for a partial value. A callee that needs to hand back a fully constructed value together with an error must return it inside the error value instead.

**Caller-side state after a fallible `out` call.** When a function with an `out` parameter returns `Result[_, E]`, the call must be consumed in the same statement by `?` or by `match`; storing, ignoring, or otherwise using the result is `INIT_OUT_RESULT_UNHANDLED`. After `f(out x)?`, `x` is initialized (the error path left the function). In `match f(out x) { Ok(v) => A, Err(e) => B }`, `x` is initialized throughout `A` and uninitialized throughout `B`. At the join after the `match`, `x` is initialized iff it is initialized on every incoming path; a join with mixed states is `INIT_CONDITIONAL`, with the machine-applicable fix of inserting `drop(x)` on the initialized path or initializing `x` on the other. An infallible `out` call (returning no `Result`) initializes `x` unconditionally.

`out` exists so that large values are constructed in place: `Box.new_with(init: func(out T) -> Result[(), E])`-style APIs construct directly in the destination with no intermediate copy.

### 5.3 Named access, projections, and the elision rule *[ADR-4]*
Only three forms bind an access to a name. All are lexically scoped, and the access ends at the closing brace:
1. `with n1, ..., nk := <projection> { ... }` — binds one name per access returned by the projection (one for a single access, several for a tuple of accesses). Alternatively the subject is a move-only owned value: the block then owns it, `n1` is an `edit` of it for the block, and it is destroyed at block exit (including early exit). `thread.scope() -> own Scope` is used this way; `Scope`'s destructor joins every thread it spawned.
2. `match <place or projection> { Variant(a, b) => ... }` — arm bindings are views (or edits, when the subject is an edit) of the matched place for the arm. Alternatively the subject is an owned value (a temporary, or `move x` for an owned local): the `match` consumes it; on entering an arm, the bound payload fields are moved into arm-owned locals, unbound payload fields are destroyed, and nothing of the subject remains afterwards. An owned subject whose type declares a destructor (§5.7) must not be destructured this way (`OWN_DESTRUCTURE_DESTRUCTOR`); match it as a place and use `take` on its fields instead.
3. `for x in <place or projection> { ... }` — per §4.

There are no reference-typed `:=` locals. Binding a projection with `:=` is `ACC_UNBOUND_PROJECTION`.

A **projection** is an expression denoting a sub-place: field access `s.f`, indexing `a[i]`, slicing `a[i:j]`, or a call to a function whose return type is `view[U]`, `edit[U]`, or a tuple of those. A returned projection is expression-scoped: it must be consumed in the same statement as an argument, an assignment target, a `with`/`match`/`for` subject, or a read of a `Copy` field.

**Elision rule.** A function is permitted to return `view[U]`, `edit[U]`, or a tuple of those only if it has exactly one `view`/`edit` parameter (a receiver counts). Every returned access is derived from that parameter and carries its root place. Two or more candidate parameters is `ACC_AMBIGUOUS_SOURCE`. Returning an access derived from a local is `ACC_ESCAPE_RETURN`. Returning an access that carries a pending release function (one obtained from an accessor with `release`, directly or through a binding) is `ACC_RELEASE_ESCAPE`: release obligations never transfer across a return, so a release-bearing access is consumed only within the function that obtained it. Returning an access derived from multiple sources is not expressible. **Permission rule:** a returned access must not be stronger than its source: a function whose single access parameter is `view` must not return `edit` (`ACC_PERMISSION_ESCALATION`). **Multi-access rule:** a function returning a tuple of two or more accesses must be implemented inside `unsafe` (or compose only such functions), and its documented contract must state that the returned accesses are pairwise disjoint, enforced by a runtime check that traps (for example `get2(a, b)` traps when `a == b`).

**Accessor release.** A function returning an access is permitted to declare a release function: `func lock(view self) -> edit[T] release unlock`. The release function receives the same receiver and runs exactly once when the returned access ends: at the end of the consuming statement, at the closing brace of the binding `with`/`match`/`for` block, or on early exit from that block by `return`, `?`, `break`, or `continue`. A trap (§6) runs no release functions. Release functions run in reverse order of access creation.

**Runtime-exclusive escalation.** `Mutex[T].lock(view self) -> edit[T] release unlock` returns an access stronger than its `view` receiver. This escalation is an enumerated unsafe operation (§6): it is permitted only inside `unsafe`, and the implementation's documented contract must state the runtime mechanism (here, the lock) that guarantees exclusivity for as long as the access is live. The checker treats the returned `edit` as rooted at the `Mutex` value, so the mutex itself is frozen for the block, which is why a `Shared[Mutex[T]]` is viewable from many threads while each lock holder has an exclusive `edit`. Buffer-pool `pin(view self, id) -> edit[Page] release unpin` follows the same pattern.

### 5.4 Aliasing check *[ADR-1]*
**Accesses.** Every operation on a place is classified as one of: `view` (read); `edit` (write-capable, leaves the place initialized: in-place mutation, whole-place reassignment `place = v` which destroys the old value then stores `v`, `take(place)`, and `replace(place, v)`); or `consume` (leaves the place uninitialized or moved: moving out by a by-value use of a move-only place, including passing to `own`, returning, storing elsewhere, and explicit `drop(place)`). A fourth class, `init`, is created by passing a place as an `out` argument: it is exclusive, begins when the argument is evaluated, ends when the call returns, and conflicts with every other simultaneously live access to an overlapping path, including a second `init` of the same place in the same call (`ACC_CONFLICT`). `consume` and `init` are the strongest accesses.

**Derived accesses.** An operation that goes *through* a bound access name (a `with`/`match`/`for` binding, or an `edit`/`view` parameter) creates a *derived* access whose root is that binding, not the binding's own root place. A derived access must not be stronger than the binding (`ACC_PERMISSION_ESCALATION`); `consume` through a binding is never permitted (`OWN_PARTIAL_MOVE`), so moving a value out through an `edit` is done with `take` or `replace`, which are `edit` accesses. While a binding is live, its underlying root place must not be accessed except through the binding (`ACC_CONFLICT`); this is how a bound name continues, rather than conflicts with, its enclosing access.

**Access lifetimes within a statement.** Accesses are checked for conflict only while simultaneously live, and liveness follows the evaluation order of §4: a read of a `Copy` value is an access that begins and ends at the moment the value is read, producing a value with no access attached; an argument access begins when that argument is evaluated and ends when the call returns; a returned projection's access lasts until the consuming operation (§5.3) completes, or for the whole block when it is a `with`/`match`/`for` subject; the `edit` access of an assignment target begins only after the right-hand side has been fully evaluated and ends when the store completes. Consequently `total = total + u64(b)` is accepted: the read of `total` ends before the write begins. Every live enclosing binding (§5.3) is live throughout the statement.

**Conflict.** Two simultaneously live accesses with the same root **conflict** iff their paths overlap and at least one is `edit`, `consume`, or `init`. Paths overlap iff one is a prefix of the other; or they index the same array or sequence with indices that are not both compile-time constants with different values; or either is a sub-slice `a[i:j]` of the same array or sequence, unless both the slice bounds and the other index or bounds are compile-time constants and the ranges are disjoint. Accesses with different roots never conflict. A conflict involving a `consume` is `OWN_USE_AFTER_MOVE` when the consumed place is a variable, and `ACC_CONFLICT` otherwise; all other conflicts are `ACC_CONFLICT`. Any access to a root place that is already moved is `OWN_USE_AFTER_MOVE`.

**Multi-access bindings.** The names bound by a single `with` from one tuple-returning projection are distinct roots and therefore never conflict with each other; their pairwise disjointness is the responsibility of the callee's contract (§5.3 multi-access rule), which is why such functions are unsafe-implemented. The projection's own root place is frozen for the block as above.

The check is syntactic path disjointness plus lexical scope. There is no non-lexical lifetime inference. The only static disjointness facts the checker uses are the compile-time constant cases in the overlap definition above (two constant indices with different values, or constant index/slice bounds whose ranges are disjoint); every other pair of indices or slices into the same array or sequence is treated as overlapping, and disjointness is then established only at runtime by a multi-access function (§5.3), whose check `show-bounds-checks` reports.

**`Interior`** is a derived marker property: a type is `Interior` iff it or any field is a type declared with `unsafe assert Interior for T` (the standard library declares it for `Mutex`, `Atomic`, and `Shared`, whose runtime state changes through a `view`). **Normative aliasing guarantees.** For the duration of a call: an `edit` parameter is the only live access to its place; a `view` parameter of a non-`Interior` type is one of possibly many live `view`s and no write to the place occurs; a `view` parameter of an `Interior` type is one of possibly many live `view`s and writes to the place's interior state are permitted from the declaring module's unsafe code. Generated code must preserve these guarantees. *Implementation guidance (non-normative):* with an LLVM backend, `edit` maps to `noalias`, non-`Interior` `view` to `noalias readonly`, and `Interior` `view` to no attribute. `unsafe assert Interior for T` is an enumerated unsafe operation (§6); its obligation is that every write through a `view` of `T` is made data-race-free by the type's own synchronization (atomics or a lock). *(resolved in Phase 4: the aliasing experiment in `bench/REPORT.md` measured no throughput change from the `noalias`/`readonly` attributes on the container workloads, so the attributes are kept as emitted but no performance claim rests on them; `Interior` views carry no attributes and that is the only correctness obligation)*

### 5.5 Concurrency *[ADR-7]*
- **`Send`** (the value is permitted to move to another thread) and **`Share`** (a `view` of the value is permitted to be read concurrently from several threads) are compiler-derived marker properties computed structurally from fields. Raw pointers, non-atomic interior-mutable cells, and thread-affine handles are neither. `unsafe assert Send for T` and `unsafe assert Share for T` opt in with documented obligations. No user-defined trait machinery is required for these markers.
- **Transfer:** `thread.spawn(f: func(own args...) -> R, own args...) -> Result[Thread[R], SpawnErr]`. Every argument type and `R` must be `Send` (`SEND_NOT_SEND` otherwise). On `Err`, the arguments have been destroyed and no thread exists. `Thread[R].join(own self) -> R` blocks until the thread completes and returns its result; destroying a `Thread[R]` without joining detaches it, and a detached thread destroys its own result when its function returns.
- **Scoped sharing:** `with s := thread.scope() { ... s.spawn(f, args...) ... }`. `s.spawn` returns `Result[Join[R], SpawnErr]`; `R` must be `Send`. On `Err`, `own` arguments have been destroyed, `view`/`edit` arguments are released, and no thread exists. Arguments are permitted to be `view` (requires `Share`, `SHARE_NOT_SHARE` otherwise), `edit` (requires `Send`), or `own` (requires `Send`). Every access passed to `s.spawn` is treated as live until the end of the enclosing `with s` block, which joins every thread it spawned before the block exits, including when a later `s.spawn` returns `Err`. Therefore each such access must be rooted in a variable or binding whose scope encloses the `with s` block; an access rooted in a variable or binding declared inside the block (including one from an inner `with`/`match`/`for`, whose release function would run before the join) is `ACC_LIVE_ACROSS_SPAWN`. This block-long extension is the only cross-thread borrow in the language and is hard-coded to the `with` block. `Join[R].get(own self) -> R` blocks until that thread completes and returns its result; it is callable inside or after the block. `Join[R]` is `Send`. At block exit the scope joins each thread; if that thread's `Join[R]` is still alive, the result is stored in it and is returned by a later `get` or destroyed when the `Join[R]` is destroyed; if the `Join[R]` was already destroyed, the scope destroys the result at the join.
- **Shared ownership:** `Shared[T]` is an atomically reference-counted immutable value; it is `Share` iff `T: Share`, and `Send` iff `T: Send` and `T: Share` (the last owner, on any thread, destroys `T`, so `T` must be transferable). The reference count is a `usize`; `clone` when the count equals the maximum `usize` traps with kind `overflow`, so the count never wraps and destruction is never premature. `Mutex[T]` is `Send` and `Share` iff `T: Send`; `with g := m.lock() { ... }` binds `g: edit[T]` for the block.
- **Atomics:** `Atomic[T]` for `T` in `u8 u16 u32 u64 usize i8 i16 i32 i64 isize bool`, an `Interior` type. Operations, every ordering argument a compile-time constant of `enum Ordering { relaxed, acquire, release, acq_rel, seq_cst }`: `load(view self, ord) -> T` with `ord` in `relaxed | acquire | seq_cst`; `store(view self, v: T, ord)` with `ord` in `relaxed | release | seq_cst`; `swap(view self, v: T, ord) -> T`; `compare_exchange(view self, expected: T, desired: T, success: Ordering, failure: Ordering) -> Result[T, T]` (strong: never fails spuriously) and `compare_exchange_weak` with the same signature (permitted to fail spuriously, returning `Err(current)` with `current == expected`) (`Ok(old)` on success, `Err(current)` on failure; the permitted `failure` orderings are: for `success = relaxed`: `relaxed`; `acquire`: `relaxed`, `acquire`; `release`: `relaxed`; `acq_rel`: `relaxed`, `acquire`; `seq_cst`: `relaxed`, `acquire`, `seq_cst`); `fetch_add`, `fetch_sub`, `fetch_and`, `fetch_or`, `fetch_xor` `(view self, v: T, ord) -> T` for integer `T` only, wrapping on overflow; `fence(ord)` with `ord` in `acquire | release | acq_rel | seq_cst`. Any other ordering argument is `ATOMIC_INVALID_ORDERING`. All read-modify-write operations accept every ordering. The memory model is the ISO C++ 2020 (ISO/IEC 14882:2020) memory model, including its definitions of happens-before and release sequences; the orderings are `relaxed`, `acquire`, `release`, `acq_rel`, and `seq_cst`. Volatile MMIO is a separate unsafe operation and is never conflated with atomics.
- Data-race freedom follows from: within a thread `edit` is exclusive (§5.4); across threads only `Share` values are viewed and only `Send` values are moved; cross-thread mutation happens only through an exclusive scoped `edit` argument (which the checker treats as live and exclusive for the whole scope block), inside `Mutex`, or through atomics.
- Lock-free structures are permitted to use audited unsafe internals behind a safe API.
- `Mutex[T].lock` is specified in §5.3 (runtime-exclusive escalation); the lock is released when the bound `edit` ends, including on every early exit of the `with` block.

### 5.6 Arenas and handles (library, not type system) *[ADR-2]*
There are no regions in the type system. `Arena[T]` (bump, freed as a whole), `Pool[T]` (free list with generation counters), and `Slab[T]` are standard-library owned containers with audited unsafe internals. A handle (`ArenaId[T]`, `PoolId[T]`) is a `Copy` integer-like value that is permitted to be stored anywhere, including inside objects in the same container; this is how trees, graphs, parent pointers, and cycles are expressed in safe code. Dereference is a projection: `get(id) -> view[T]`, `at(id) -> edit[T]`, `get2(a, b) -> (edit[T], edit[T])` (traps when `a == b`). A successful dereference requires, in this order: the slot index is within bounds (else trap kind `bounds`); in debug builds, when both the handle's and the container's identity tags are nonzero, they are equal (else `identity`); the slot is occupied by a live, fully initialized element (else `vacant`); the slot's generation equals the handle's generation (else `generation`).

**Validity.** A handle is not bound to a container. Using a handle with a different container of the same element type is a logic error: it is memory-safe (bounds and generation are checked against the container actually used), and in debug builds every container carries a 32-bit identity tag that is also stored in handles it issues and checked on dereference, trapping on mismatch. Tags are drawn from a process-global atomic counter starting at 1 and are never reused; tag 0 means "unchecked", and once the counter is exhausted every further container receives tag 0, which disables the identity check for it without affecting memory safety. A stale generation traps. Memory safety holds regardless because every slot is always valid memory of the right type. Logical validity (runtime) and memory safety (static) are distinct guarantees. **Generation exhaustion:** generations are 32-bit; when a slot's generation would wrap, the slot is retired and never reused, so stale-handle detection remains guaranteed for the container's lifetime. A container destroys its live contents when destroyed; `Pool.free(id)` performs the same checks in the same order as dereference (so a repeated free of a not-yet-reused slot traps with kind `vacant`, a free with a handle whose slot was reused traps with `generation`, and a foreign handle traps with `identity`, `vacant`, or `generation` as those checks dictate), then runs the element destructor and increments the slot's generation.

**Reserved extension, not in the core *(resolved in Phase 5: not adopted; no §8 workload needed it, `docs/reports/phase-0-workload-summary.md`)*:** *view-kinded aggregates*. A struct declared `view struct` is permitted to contain `view`/`edit` fields and is itself second-class: producible only by §5.3, bindable only by `with`/`match`/`for`, passable only as `view`/`edit`, never stored or otherwise returned. This provides borrowing iterators and reference-holding cursors without annotations. It is added iff Phase 0 shows at least one §8 workload requires it; the Phase 0 report must state the count, and Phase 0 passes only if that count is at most two (§11).

### 5.7 Destructors
- A type declares at most one destructor, `destructor(edit self) { ... }`, in the type's own module. A type with a destructor, or with any field whose type has a destructor, is move-only (§5.1).
- When an owner is destroyed (scope exit, reassignment, `drop(x)`, container destruction, `Pool.free`), the runtime first runs the type's destructor with `self` bound as an `edit` access, then destroys the fields in reverse declaration order (each recursively by this rule). Array elements are destroyed from the last index to the first.
- Inside the destructor, `self` is reachable only through the `edit self` binding; moving `self` or a field out is `OWN_PARTIAL_MOVE` (use `take`/`replace`). The destructor must not return a value and must not be called explicitly; `drop(x)` is the only explicit destruction operation and consumes `x`.
- **Non-reentrancy.** Because a value has exactly one owner and destruction consumes that owner, no other access path to the value exists while its destructor runs, so the destructor of a given value runs at most once and never observes itself running. A trap inside a destructor terminates (§6).
- `Copy` types have no destructor by definition, and destruction of a `Copy` value is a no-op.

### 5.8 Adversarial cases
Each must have a fixture and a one-page note stating whether it is expressible in safe code, requires audited unsafe internals behind a safe API, or is rejected by design:
intrusive linked lists (unsafe internals, handle API); self-reference, parent pointers, cycles (handles); interior pointers after container growth (rejected by §5.4); two simultaneous edits into one pool (`get2`, runtime disjointness); FFI lifetime mismatch (owned registration object whose destructor unregisters); partially initialized objects (`out` + definite initialization); destructor reentrancy (impossible, §5.7); concurrent container access (`Send`/`Share` derivation, `Mutex`); large-object construction without copies (`out`). Callbacks retaining references are not an adversarial case: they are not expressible in safe code. Async suspension and cancellation are out of scope; the recorded constraint is that no `view`/`edit` is permitted to be live across a suspension point in any future async design, which must be built from owned state machines.

## 6. Runtime and low-level support
No mandatory GC or scheduler. Define startup, trap behavior, TLS, stack checks, OOM handling, allocation APIs, and a freestanding mode with no OS assumptions. **Stack exhaustion** on every target is a trap of kind `stack`: hosted targets use a guard page and the runtime's signal or exception handler; freestanding targets use a compiler-inserted stack-limit check in every function prologue (disabled only by an explicit unsafe build option, which then documents stack overflow as a trusted-boundary obligation). Support explicit heap allocators, arenas, slab pools, and custom page allocators as library types (§5.6). Track allocator lifetime versus object lifetime: a container owns its allocator or holds it by `own Shared[Allocator]`.

**Trap semantics *[ADR-6]*:** A panic is a trap. A trap runs no destructors and no release functions, unwinds no frames, and must not be caught or resumed. The runtime invokes the registered trap handler, `func(view TrapInfo)`, at most once on the trapping thread (a trap inside the handler terminates immediately), then terminates: in freestanding mode by halting, in hosted mode by aborting the process. `trap.set_handler(f: func(view TrapInfo)) -> func(view TrapInfo)` installs `f` process-wide as a single atomic `seq_cst` exchange and returns the previously installed handler; a trapping thread selects the handler by one atomic `seq_cst` load at the moment of the trap, so concurrent replacements are totally ordered and each trap runs exactly one handler; the default handler writes `TrapInfo` to standard error in hosted mode and is a no-op in freestanding mode. `TrapInfo` carries the trap kind (`bounds`, `overflow`, `div_zero`, `shift`, `conversion`, `generation`, `vacant`, `identity`, `disjoint`, `oom`, `stack`, `explicit`, `unreachable`), the source location, and the thread identifier. The trap handler is the only cleanup hook; programs that must flush or release external resources on failure do so there, without relying on destructors. Errors that a program is expected to handle are values (`Result[T, E]`) with `?` propagation. Consequence: no landing pads, no exception-safety obligations in unsafe code, static destructor points.

**Allocator interface.** `interface Allocator { func alloc(edit self, size: usize, align: usize) -> Result[RawPtr, AllocErr]; func free(edit self, ptr: RawPtr, size: usize, align: usize) }`, with `union AllocErr { OutOfMemory }`. Obligations: `align` must be a power of two not exceeding 4096, and `size` a multiple of `align`, else the implementation traps with kind `explicit`; a successful `alloc` returns uninitialized memory of at least `size` bytes whose address is a multiple of `align`, owned by the caller until passed to `free`; `free` must receive exactly the `ptr`, `size`, and `align` of one prior successful `alloc` on the same allocator, exactly once, and the memory is then no longer the caller's (both are unsafe raw-pointer operations). `size == 0` is permitted and returns a unique non-null pointer that must still be freed. `edit self` makes an allocator exclusive; an allocator shared between threads is `Shared[Mutex[A]]` or an `Interior` allocator with internal synchronization. Every container that allocates takes `own A` where `A: Allocator`, or `own Shared[Mutex[A]]`; the hosted standard library provides `SystemAllocator`, and the freestanding mode provides none (ADR-11 decides which, if any, becomes mandatory).

**OOM:** `alloc` returns `Err(OutOfMemory)`; convenience constructors (`Box.new`) trap on it with kind `oom`.

**Unsafe:** raw pointers, pointer arithmetic, memory-mapped registers, volatile access, packed/unaligned access, inline assembly, allocator internals, `assert Send/Share/Interior`, multi-access returns and runtime-exclusive escalation (§5.3), writes through a `view` of an `Interior` type inside its declaring module, and the FFI operations of §7. `unsafe` authorizes exactly these enumerated operations; conventions, moves, initialization, and types are still checked inside `unsafe`. Each safe wrapper over unsafe internals must carry a contract block on its declaration: `contract { invariant "..."; requires "..."; ensures "..." }`, with zero or more of each clause, each clause a string. A function containing `unsafe` without a contract block is `UNSAFE_MISSING_CONTRACT`. `explain-ownership` surfaces the block as `{"invariant": [string], "requires": [string], "ensures": [string]}`.

## 7. Compiler architecture
The pipeline below is illustrative; the normative requirements of this section are the observable behaviors, the IR invariants, the testing rules, and the machine API.
```text
source / structured agent edits
 -> lexer/parser -> canonical AST
 -> name and type resolution
 -> ownership / initialization / access / Send-Share checker
 -> typed, ownership-aware semantic IR
 -> checked lowering and optimization (IR validator after every pass)
 -> native backend -> native objects / freestanding binaries
```
**Normative behavior.** The compiler must expose the semantic IR (`emit-ir`), must execute it directly in an interpreter mode that is available from Phase 1, and must produce native objects with the C ABI from Phase 2 and freestanding targets from Phase 3.

**C ABI subset (Phase 2).** A function declared `extern "C"` (exported or imported) uses the target's C calling convention and an unmangled symbol equal to its name. Its parameter and return types must be: integer types, `f32`, `f64`, `bool`, raw pointers, or `Copy` structs whose fields are recursively of these types (laid out per §4.1); any other type, including `own`/`view`/`edit`/`out` parameters, slices, unions, and generics, is `FFI_UNSUPPORTED_TYPE`. Variadic functions are not supported. Calling an imported `extern "C"` function is an unsafe operation; exporting one is safe, and a trap inside it terminates per §6.

**Prototype implementation notes (non-normative).** The prototype compiler is written in Go; the compiler's own GC does not imply GC in produced programs. The native backend emits textual LLVM IR and invokes `clang`/`llc`, which avoids native bindings; a C-emitting backend is the fallback for targets LLVM does not serve.

**Checked lowering** (not verified compilation). The semantic IR carries explicit instructions or attributes for: `move`; `drop` (static); `access_begin`/`access_end` for every convention and scoped access; `check_bounds`; `check_generation`; `check_disjoint`; `unsafe_begin`/`unsafe_end`; and a provenance tag on every check. An IR validator must assert after every pass:
1. For every ownership instance, every path from its initialization to the end of the function performs exactly one of: a `drop`, a `move` out (including return and transfer to an `own` parameter or container), or a trap; no use of the instance follows its `drop` or `move`. Trap paths terminate and carry no `drop` obligations (§6).
2. Every `access_begin` has a matching `access_end` in the same function, and no two accesses that conflict under §5.4 (overlapping paths, same root, at least one `edit`, `consume`, or `init`) are open at once.
3. Every `check_*` either remains or is replaced by a recorded proof fact (`proven_by: loop_bound | dominated_by_check | constant`).
4. No instruction outside an `unsafe` region performs an unsafe operation.
5. No second-class value flows into a store, a non-elision return, or a call argument that escapes.

**Testing.** Every fixture is tagged with the earliest phase in which it is executable: ownership, initialization, access, and trap fixtures from Phase 1; FFI fixtures from Phase 2; concurrency and freestanding fixtures from Phase 3. Before its phase a fixture is `check`-only. Every accepted fixture carries an expected-output file. From its phase, the interpreter's observable output must match it, and from Phase 2 or its phase, whichever is later, the native backend's output must match it as well (differential testing). Every rejected fixture must produce the same set of diagnostic codes from `check` regardless of backend; rejected fixtures are not executed.

**Machine API.** Every command reads one JSON request on standard input and writes one JSON response on standard output; both carry `schema_version`. Request: `{"schema_version", "command", "files": [path], "target"?: string, "span"?: {"file": path, "start": int, "end": int}, "edit"?: <structured edit>}`. `span` names one of `files` and is required by `explain-ownership` (`API_MISSING_SPAN` otherwise) and ignored by every other command. `target` is an LLVM-style target triple; when absent, the host target is used. Every result is computed for that target; exactly the results of `show-layout`, `show-copies`, `show-effects`, and `emit-asm` carry a `target` field. Response: `{"schema_version", "ok": bool, "result": <command-specific object>, "diagnostics": [diagnostic]}`. Failure: `ok=false`, a non-empty `diagnostics` array, and exit code 2 for user errors or 3 for internal errors. Diagnostics carry stable codes, spans, related locations, the violated rule number, and optional machine-applicable fixes. Every code (`OWN_*`, `INIT_*`, `ACC_*`, `SEND_*`, `SHARE_*`, `UNSAFE_*`) maps to one numbered rule in the language reference. Commands: `check`, `format`, `explain-ownership`, `show-layout`, `show-allocations`, `show-copies`, `show-effects`, `show-bounds-checks`, `emit-ir`, `emit-asm`, and `apply-structured-edit`. The `result` schema of each command and the structured-edit format are specified normatively in §16; `tools/agent-api/schema.md` is the machine-readable copy and must match §16 for the same `schema_version`. Every reported fact is labeled `proven`, `runtime-checked`, `assumed-unsafe`, `estimated`, or `unknown`; the label is derived from the IR provenance tags, never from heuristics. Results whose schema in §16 carries no `label` field (`check`, `format`, `show-layout`, `emit-ir`, `emit-asm`, `apply-structured-edit`) are `proven` by construction and are exempt.

Example diagnostic:
```json
{"schema_version":"0.2","ok":false,"result":null,"diagnostics":[{"code":"OWN_USE_AFTER_MOVE","severity":"error","rule":"5.1.4","file":"main.ai","span":{"start":128,"end":134},"related":[{"label":"moved here","start":91,"end":97}],"fix":null,"op_index":null}]}
```

## 10. Decisions
**Decided in v0.2 (each has an ADR with alternatives and counterexamples):**
- ADR-1: Second-class access (conventions + lexical scopes) instead of first-class references. No escaping safe references except §5.3.
- ADR-2: Arenas, pools, and handles as library types; no regions in the type system.
- ADR-3: Static moves, no partial moves, no drop flags; implicit moves at by-value use, explicit deep copies.
- ADR-4: Single-source elision rule for returned projections; permission never escalates in safe code, with runtime-exclusive escalation as an enumerated unsafe operation; multi-access returns are unsafe-implemented with runtime disjointness.
- ADR-5: `out` convention for in-place construction, with static per-field cleanup on error.
- ADR-6: Panic is a trap; no unwinding, no destructor cleanup; a single trap handler hook.
- ADR-7: Derived `Send`/`Share`; scoped spawn is the only cross-thread borrow; thread results must be `Send`.

**Open, in order *[ADR-8..11]*:**
- ADR-8: Bounds and generation checks on by default (recommended) and provenance of eliminated checks.
- ADR-9: Generics: monomorphized with nominal interface constraints (`interface`/`impl`); `Copy`, `Send`, `Share` usable as constraints; no dynamic dispatch in the core, and when added, `dyn I` is an explicit owned box or explicit view.
- ADR-10: Function pointers now; non-escaping closures later; no escaping closures.
- ADR-11: Which freestanding runtime facilities are mandatory.

Each ADR records: problem, alternatives, invariants, hard counterexample, expressiveness cost, performance cost, complexity, experiments, and conclusion.

**Structured edit** (`edit` in the request): `{"ops": [op]}` where `op` is one of `{"op": "replace_span", "file": string, "span": span, "text": string}`, `{"op": "insert", "file": string, "at": int, "text": string}`, `{"op": "delete_span", "file": string, "span": span}`, or `{"op": "rename_symbol", "file": string, "span": span, "new_name": string}` (renames the declaration at `span` and every resolved use of it across the request files). **Application semantics:** (1) every `rename_symbol` op is first resolved against the unedited files and expanded into one `replace_span` per declaration or use, each attributed to the rename op's index (`EDIT_UNRESOLVED_SYMBOL` if the span is not a resolvable declaration); (2) all resulting ops refer to the files as they were before the edit; (3) two non-insert ops in the same file conflict iff their spans intersect, and an `insert` at offset `k` conflicts with a non-insert span `[s, e)` iff `s < k < e`; inserts at the same offset do not conflict; (4) the resulting text of each file is defined as follows: each non-insert op replaces its span `[s, e)` with its text (empty for `delete_span`); an insert at offset `k` places its text immediately before any original byte at `k`, which puts it before the text of a replacement starting at `k` and after the text of a replacement ending at `k`; several inserts at the same offset appear in request order; (5) a span is invalid if `start < 0`, `start > end`, `end` exceeds the file length, either boundary is not on a UTF-8 character boundary, or a `replace_span`/`delete_span` span is empty (use `insert`); an insert offset is invalid if `at < 0`, `at` exceeds the file length, or `at` is not on a UTF-8 character boundary (both `EDIT_INVALID_SPAN`); (6) application is all-or-nothing: on any conflict or invalid coordinate `ok=false`, no file changes, and one diagnostic with code `EDIT_OVERLAP`, `EDIT_UNRESOLVED_SYMBOL`, or `EDIT_INVALID_SPAN` names the offending op by index. A `fix` carried by a diagnostic is a structured edit in this format.
